# Architecture

This document records the decisions behind `@neuronautix/myst` v0.2 and the MyST behaviour they
were verified against. Where a decision departs from what seemed obvious at the outset, the
reason is stated.

Verified against **mystmd 1.10.1** (`myst-common` 1.10.0, `myst-parser` 1.7.3) and the
`dhuzard/oratlas` repository as of August 2026.

---

## 1. Trust boundary

```
┌─────────────────────────────────────────┐
│ MyST publication                        │   static, immutable per version,
│  source .md, myst.yml, references.bib   │   owned by the author
│                                         │
│  ├── myst.xref.json      (MyST)         │
│  ├── oratlas.manifest.json  (this pkg)  │
│  └── oratlas/claims.jsonl   (this pkg)  │
└────────────────┬────────────────────────┘
                 │  fetch + verify, one direction only
┌────────────────▼────────────────────────┐
│ ORAtlas                                 │   mutable, federated,
│  canonical graph identity               │   owned by the platform
│  cross-publication evidence relations   │
│  TRUST assessments and verification     │
│  challenges, adjudication, discussion   │
│  curation, aggregation, synchronisation │
└─────────────────────────────────────────┘
```

The arrow points one way. A MyST build never contacts ORAtlas; validation never contacts
anything. That is not a convenience choice — it is what makes a published version's artifacts
independently checkable years later, by someone with the source bytes and nothing else.

**What the publication may assert:** what it declares, where it declares it, and what bytes it
declared it over. All of that is true forever about that version.

**What only ORAtlas may assert:** whether the claim is supported, whether two claims are the
same claim, what anyone thinks of it. All of that changes, so a static file cannot hold it
without lying.

This is why there is no per-claim score in the format. ORAtlas's TRUST model assesses a
specific _claim–evidence relation_ against ten criteria with an explicit protocol version, and
its aggregate is advisory and method-tagged. A single number attached to a claim is not a
simplification of that model; it is a different, incompatible thing.

## 2. Decision A — how a claim becomes a MyST target

**Decision: the directive lowers to a standard MyST `div` node carrying `identifier`, `label`,
`class` and `data`.**

MyST's `enumerateTargetsTransform` visits _every_ node and registers it as a cross-reference
target when it has an `identifier` and its type is not in a small exclusion list
(`crossReference`, `cite`, `footnoteDefinition`, `footnoteReference`, `captionNumber`, `link`).
`writeMystXRefJson` then emits one `myst.xref.json` entry per registered target, with
`kind` derived from the node type.

So a `div` with an `identifier`:

- appears in `myst.xref.json` as `{"identifier": "...", "kind": "div", "data": "...", "url": "..."}`;
- gets an `html_id` generated by MyST, making it addressable in the built page;
- renders as a plain block wrapper in web themes, and passes its children straight through in
  the LaTeX, Typst and DOCX exporters;
- is not enumerated or numbered, because `shouldEnumerateNode` finds no numbering entry for
  `div` and the default is off.

Alternatives considered:

- **`container`** — `kindFromNode` returns `node.kind || TargetKind.figure`, so a container
  without a custom kind becomes a figure and picks up figure numbering. A custom kind avoids
  the numbering but makes the node a figure-shaped thing that themes render with figure
  chrome. Wrong shape for a paragraph of prose.
- **`admonition`** — renders with a callout box and a title bar in every theme. That is a
  visual decision imposed on every reader of every publication, which is not this package's
  call to make.
- **Labelling the first block of the body directly** — no wrapper node, but then a
  multi-paragraph claim has no single node to carry the identifier or the metadata.

**Known cost:** `[](#claim-id)` with empty link text renders as the literal word "Div".
`addChildrenFromTargetNode` fills empty reference text from a `caption`, `admonitionTitle` or
`definitionTerm` inside the target, and falls back to the kind name otherwise. A `div` has
none of those. Injecting a `caption` into a `div` to work around this would put a node where
no theme expects one. The documented guidance is to write explicit link text, which reads
better regardless.

**No custom renderer is required to read the article.** MyST 1.10.1's plugin surface is
`{ name, author, license, directives, roles, transforms }` — there is no `renderers` key, and
custom renderer plugin hooks remain documented as not yet implemented. v0.1 is built entirely
on directives, and the scientific text survives as ordinary MyST nodes in every output format.

## 3. Decision B — how the exporter finds claims

**Decision: the CLI parses the project's source directly with `myst-parser`, registering the
same `oratlas:claim` directive spec the plugin uses.**

The three candidates were:

1. **A `stage: "project"` transform inside the plugin, writing files as a side effect.** MyST
   transforms are not a documented file-writing extension point; ordering and completeness
   guarantees are unclear; and it would tie artifact generation to a full build.
2. **Reading `_build/site/content/*.json` after a site build.** Accurate about the final AST,
   but requires a complete build (and therefore a resolvable theme, which means the network),
   and the post-build AST no longer carries byte-exact source spans — MyST's directive body
   positions collapse to a single line/column pair.
3. **Direct source parsing.** Chosen.

Direct parsing wins on every axis that matters here:

- It works with no build at all, so `export` and `validate` are fast and offline.
- `data.node.value` gives the **directive body exactly as written in the source**, and
  `data.node.position` gives an exact line span. Both are needed for byte-accurate digests and
  selectors; neither survives into the built AST.
- It avoids depending on `myst-cli` (72 dependencies) or on its internals.
- It is fully deterministic and unit-testable.

The cost is that the exporter does not know the site's slugs or URLs. That is deliberate: those
belong to the build and are already published by MyST in `myst.xref.json`, which the manifest
points at. Reproducing them here would create a second, staler authority for the same fact.

Page discovery: `project.toc` when `myst.yml` declares one (order preserved, both the legacy
nested shape and the `myst-toc` shape traverse identically), otherwise a sorted directory walk
skipping dotfiles, `node_modules`, `_build`, `_static`, `_templates` and the output directory.

## 4. Decision C — what each digest covers

**Decision: three digests over three different units.** No single digest can answer the three
questions a consumer actually asks, so the format does not pretend one can.

| Digest                  | Covers                                                                    | Answers                                                     |
| ----------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `source.documentSha256` | the declaring document's complete UTF-8 bytes                             | _Is this the same version of the page?_                     |
| `source.blockSha256`    | the exact source lines of the directive block                             | _Did this declaration's source block change?_               |
| `declarationSha256`     | canonical JSON of `{schemaVersion, id, body, claimType?, qualification?}` | _Did the author's assertion change, wherever it now lives?_ |

`documentSha256` is the one that buys interoperability. ORAtlas computes exactly this — SHA-256
over the page's UTF-8 source bytes — as `sourceSha256` in its `PassageCommentAnchor`
(`apps/web/src/lib/article-reader.ts`, `apps/web/src/lib/hash.ts`). Emitting the identical
value means a claim record and a passage annotation agree, without translation, on which
version of a page they are discussing.

`declarationSha256` is the granular one. Excluding the path and line span means moving a claim
within or between documents, unchanged, keeps its digest. Including `id` means two
byte-identical statements under different ids get different digests — because they are
different declarations. `canonicalJson` here is a deliberate re-implementation of ORAtlas's,
with identical behaviour, so a digest recomputed on either side matches.

The `body` input is the raw source, not the derived plain text. Normalising before hashing
would make the digest insensitive to changes the author can see, which is the opposite of what
it is for.

**What the digests do not establish.** A digest says bytes did not change. It says nothing
about whether a claim is correct, supported, replicated or accepted, and the format is explicit
about that in [SPEC.md §4.3](../SPEC.md#43-what-the-digests-establish).

### Selectors

`selector` uses W3C `TextQuoteSelector` and `TextPositionSelector` objects, in exactly the
strict shape ORAtlas's schemas accept — no extra keys, so either can be handed to ORAtlas's
validator unchanged. `representation` and `unit` live on the enclosing `selector` object rather
than inside those two, precisely so the W3C shapes stay pure.

Offsets are in Unicode code points, not UTF-16 code units, matching the W3C definitions and
ORAtlas's `unicodeCodePointLength`. The frame is the **raw source text**, which is what the
document digest covers and therefore what a validator can verify locally.

That frame is explicitly _not_ ORAtlas's `myst-rendered-text-v1`, whose offsets are relative to
ORAtlas's own rendering of the page. This adapter cannot reproduce that rendering, so it does
not claim to. `representation` names the frame so the two can never be confused.

`unit` is `"body"` when the directive body appears verbatim inside the block, and `"block"`
when MyST dedented it (a directive nested inside another block). Recording which, rather than
silently falling back, keeps the quoted span byte-exact in both cases and keeps the consumer
informed.

## 5. Decision D — relationship to `review-manifest.json`

**Decision: `oratlas.manifest.json` never restates anything a declared `review-manifest.json`
already owns, and the manifest names which artifact is authoritative for claim declarations.**

ORAtlas's `review-manifest.json` (schema 1.0.0, `packages/contracts/src/manifest.ts`) is the
richer document. It declares review metadata, repository provenance, DOIs, contributors, and
paths to claims, citations, relations, TRUST assessments and provenance artifacts.

The two documents describe genuinely different facts:

- **Fact A — a claim declaration.** _Claim X states T, and is empirical._ `review-manifest.json`
  has a representation for this.
- **Fact B — a source occurrence binding.** _Claim X is declared at `results.md` lines 12–23 of
  this exact source, targetable as `#hpa-axis-mediation`, with digest D._
  `review-manifest.json` has no representation for this at all.

Fact B is what this adapter uniquely provides. Fact A is contested territory, so the manifest
resolves it explicitly with `artifacts.claims.declarations`:

- `"publication-source"` — no review manifest claims stream. Records carry `text`, `claimType`,
  `qualification`.
- `"review-manifest"` — a review manifest declares `artifacts.claims`. That stream is
  authoritative; records here carry only the identifier and the source binding.

The export fails if the MyST source declares a claim the review manifest's stream does not, and
reports (without failing) a review-manifest claim with no MyST occurrence — the latter is
legitimate, it simply has no source binding.

The review manifest is _recognised_, never reinterpreted. Only the `id` field of its claim
records is read; nothing is validated against a reimplementation of ORAtlas's contract,
rewritten, upgraded, or re-emitted. Reading a source assertion does not make it verified.

## 6. Decision E — publishing at the site root

**Decision: `project.static_files` in `myst.yml`. Verified against the mystmd 1.10.1 build,
not assumed.**

MyST resolves each `project.static_files` entry relative to the project root and copies it by
**basename**:

```js
fs.copySync(resolvedFn, join(destDir, basename(resolvedFn)));
```

For the site build (`myst build --site`) `destDir` is `session.publicPath()`
(`_build/site/public/`), which the dev server serves at `/`. For the static HTML build
(`myst build --html`) `buildHtml` calls `copyStaticFiles(..., htmlDir, proj.path)` with
`htmlDir = _build/html`, so the files land directly in the deployable site root — beside the
`myst.xref.json` that same function writes.

So:

```yaml
project:
  static_files:
    - .oratlas/oratlas.manifest.json # → /oratlas.manifest.json
    - .oratlas/oratlas # directory → /oratlas/claims.jsonl
```

The basename-only copy is what makes this work cleanly: the generated tree under `.oratlas/`
mirrors the published layout, so `.oratlas/oratlas/claims.jsonl` becomes `/oratlas/claims.jsonl`.

`tests/myst-integration.test.ts` runs a real `myst build --site` against `examples/basic` and
asserts that both artifacts appear in the site's public root with byte-identical content, and
that all four claims appear in the real `myst.xref.json`.

`validate` warns when `myst.yml` does not declare these entries, since the artifacts would then
be generated but never served.

## 7. Decision F — publication identity, version and source

Added in v0.2 after review. The v0.1 manifest carried only an optional `canonicalUrl` and
title, which is not enough for ORAtlas to tell one publication from another, or version 1 of a
publication from version 2.

**A URL is not identity.** A publication can move, be mirrored, or be served from several
hosts, and two publications can occupy one URL at different times. So the manifest carries
three separate things:

- `publication.id` — _which publication this is_, stable across versions. Author-declared,
  defaulting to `myst.yml`'s `project.id`. Source-local, never minted by the adapter.
- `publication.version.sourcesSha256` — _which version this is_. Always present: a digest over
  the document set (`{path, sha256}` sorted by path), so an exact version identity exists even
  for a plain website with no repository, DOI or archive.
- `publication.source` — _where the source bytes are_, as a discriminated union over `git`,
  `doi` and `archive`.

**The two verification levels.** This is the substantive reason the source descriptor exists. A
deployed MyST site serves HTML, page JSON, `myst.xref.json` and the ORAtlas artifacts — it does
_not_ serve `results.md`. So a claim record can say `results.md` has digest `abc…` while a
consumer holding only the site has no way to obtain those bytes and check it.

```
Level 1 — published-structure verification        (every consumer)
    manifest + claims.jsonl + xref + page JSON
        └── the claim exists in the published structure, at a resolvable location

Level 2 — source-byte verification                (needs publication.source)
    + the source repository, deposit or archive
        └── documentSha256, blockSha256, declarationSha256 and the selectors
```

A journal site with no public Markdown is a first-class graph participant at level 1; a
git-backed publication additionally reaches level 2. `tests/published-structure.test.ts` runs
level 1 against a real MyST build using only published bytes, with the source deliberately out
of reach.

**Why the commit is not auto-detected.** Reading `HEAD` would make the manifest disagree with
the published bytes whenever the working tree is dirty — exactly the case where provenance
matters. And the config file naming the commit is itself part of the commit. So `commit` is
optional and supplied by the build: `oratlas-myst export --source-commit "$GITHUB_SHA"`.

## 8. Decision G — keeping the protocol toolchain-neutral

Also added in v0.2. The v0.1 manifest hard-coded MyST into the ingestion contract:
`myst: { xref }` at the top level, and a bare `{ identifier, htmlId }` target.

That is fine for this package and wrong for the protocol. The intended shape is one ORAtlas
ingestion contract with several publication-side adapters:

```
                    ORAtlas protocol
                          │
          ┌───────────────┼───────────────┐
        MyST             JATS           Quarto
          └───────────────┼───────────────┘
                          ▼
                  canonical ORAtlas graph
```

So both are discriminated unions now:

```json
"adapter": { "type": "myst", "xref": "myst.xref.json" }
"target":  { "type": "myst-xref", "identifier": "…", "htmlId": "…" }
```

A consumer switches on `type` and normalises into one generic source-occurrence
representation. `identifier` is the field every target variant must carry, because it is what
joins a claim record to the toolchain's cross-reference inventory. The canonical graph never
learns which toolchain a publication was authored in.

This was worth breaking the schema for now, while nothing consumes it, rather than after
ORAtlas has an ingestion contract built around a MyST-shaped manifest.

## 9. The inventory URL trap

`myst.xref.json` `url` values are site-root-relative absolute paths. Resolving one directly
against a canonical URL that has a path silently drops the path:

```js
new URL("/results", "https://example.org/review/").href; // "https://example.org/results"
```

Every subpath deploy hits this. `resolvePublishedUrl()` is exported so consumers do not have to
rediscover it, the rule is normative in [SPEC §6.1](../SPEC.md#61-resolving-an-inventory-url),
and a test asserts both the trap and the fix. It was found by a test, not by reasoning.

## 10. Configuration: why `oratlas.yml`, not `myst.yml`

MyST validates `project` keys strictly. A namespaced block under `project:` produces, on
**every single build**:

```
⚠️  myst.yml 'config.project' extra key ignored: oratlas (at myst.yml)
```

The configuration is ignored _and_ the author gets a permanent warning. That is not a safe
namespaced extension point, so configuration lives in a dedicated `oratlas.yml`.

The file is entirely optional; the defaults work. Its keys are `schema_version`, `id`,
`canonical_url`, `output`, `review_manifest`, `title`, `version_label`, `source`, `contributors`,
and `production`, and an unknown key is a hard error
rather than a silent no-op — a typo in a config key should not quietly disable the thing it was
meant to configure. The `source` block is validated by the same Zod union that the manifest
emits, so the config surface and the artifact can never disagree about what a valid source
descriptor is.

There is no ORAtlas server URL, because nothing here needs one.

Schema 0.3 keeps three independent channels: scholarly credit (`contributors`), explicitly
declared production provenance (`production`), and transport (`adapter`). The standard MyST
author contract is read only for scholarly credit. Nothing in dependencies, plugins, source
text, or build configuration is inspected to infer production.

The mapper is pinned to the installed `myst-frontmatter@1.10.0` contract used by the current
MyST dependencies: project `authors` expose `id`, `name`/parsed given and family names, `orcid`,
`corresponding`, `affiliations`, `url`, and collaboration/organization metadata. Only those
documented deterministic fields are read; MyST's richer CRediT `roles` are not guessed into the
bounded scholarly-role vocabulary.

## 11. Contracts and schemas

Zod schemas in `src/contracts/` are the single definition. The JSON Schemas in `schemas/` are
generated from them by `scripts/generate-schemas.ts`, with recursively sorted keys so the
output is byte-stable. `pnpm run schemas:check` fails on drift, and `tests/schemas.test.ts`
runs the same check plus Ajv validation of real generated artifacts. Hand-editing `schemas/` is
not a supported operation.

Both the manifest object and the claim record object are `.strict()`: an unknown key is an
error. The trade is deliberate — a typo cannot be silently ignored, at the cost of needing a
`schemaVersion` bump for every addition.

**`@oratlas/contracts` is deliberately not a dependency.** ORAtlas's contracts package is its
internal boundary, not the portable protocol boundary; depending on it would couple every
independent MyST publication to ORAtlas's internal release cadence. Three small pieces are
re-implemented here with identical behaviour, each marked as such in the source:
`canonicalJson`, `sha256`, and the safe-path rule.

## 12. Security posture

Publication input is untrusted throughout.

- **Path resolution** (`resolveInsideProject`, in `src/fs-safe.ts`) checks twice: lexically,
  and again on the real path after symlink resolution. Every path from a TOC entry, a config
  value, or a manifest field goes through it — including `myst.yml` and `oratlas.yml`
  themselves, which are publication input like any other file.
- **Discovery never follows a symlink.** The directory walk uses `lstatSync`, so a symbolic
  link is seen as a link rather than as whatever it points at, and is skipped. Following one
  would let a link inside the project walk the filesystem outside it, and a link to an ancestor
  directory would make the walk unbounded. A skipped link is reported to the author rather than
  silently dropped; declaring it in `project.toc` makes it an explicit declaration, which is
  then resolved with the realpath discipline above. A depth cap backs this up.
- **A refused path is not "absent".** `projectFileExists` lets an unsafe-path error propagate
  instead of returning false, so a symlinked config file is refused rather than quietly
  ignored, and an escaping TOC entry reports the traversal rather than "file not found".
- **Two path rules.** Published paths (things a consumer resolves) use the strict rule that is
  byte-compatible with ORAtlas's validator. Local paths (the output directory, TOC entries)
  use a permissive rule that still forbids escape, absolute paths, backslashes and schemes,
  but allows `.oratlas` and `_pages/` — forms the strict rule rejects and that are perfectly
  normal on disk.
- **Size and count caps**: 8 MB per document, 32 MB per JSONL artifact, 1 MB per config file,
  5 000 pages, 200 000 records.
- **No execution**: nothing from the publication is executed or evaluated. The bundled plugin
  registers one directive and injects no remote JavaScript.
- **No network**: no URL is dereferenced during export or validation. `canonical_url` is
  metadata; it is validated as a URL and never fetched.
- **Deterministic parsing**: MyST's own parser, never regular expressions over Markdown.

## 13. Determinism

Byte-identical source and configuration produce byte-identical artifacts. Concretely:

- No timestamps, run ids, random ids, absolute paths or hostnames are written anywhere.
- All string ordering uses an explicit UTF-16 code-unit comparator (`compareStrings`). Neither
  bare `Array.prototype.sort` on non-strings nor `String.localeCompare` is used anywhere —
  the latter would make output depend on the host locale.
- Page order comes from `project.toc`, or from a sorted directory walk.
- Records are ordered by `(documentPath, startLine, id)`.
- The manifest is serialised with two-space indentation and a trailing newline; the JSONL with
  one record per line and a trailing newline.
- Record key order is fixed by construction, so the file stays readable while remaining
  deterministic.

`tests/export.test.ts` asserts byte-identical output across two runs, asserts output is
unchanged under a different `LC_ALL`, and asserts no timestamp, absolute path or cwd leaks into
the artifacts. `validate` re-runs the export in memory and compares byte for byte.

## 14. MyST compatibility notes

Findings from mystmd 1.10.1, recorded because they constrain the design:

- **Plugin surface.** `MystPlugin = { name?, author?, license?, directives?, roles?, transforms? }`.
  No renderer hook. Transforms have `stage: "document" | "project"`.
- **Plugin loading.** MyST imports a plugin file directly and provides it no module resolution,
  so the artifact must be self-contained. `dist/oratlas-myst.mjs` is bundled for that reason
  (~132 kB, Node built-ins external).
- **Directive body.** `data.node.value` is the body source verbatim for an unindented
  directive; a directive nested inside another block is dedented, which is what `selector.unit`
  handles.
- **Positions.** Directive nodes carry an exact line span. Inline nodes in a reparsed directive
  body collapse to a single line/column — usable for lines, not for columns.
- **Citations.** `[@key]` parses to `citeGroup > cite`, and `cite` carries no text children
  until the build's citation transform runs. `myst-common`'s `toText` therefore drops citations
  entirely, stranding surrounding punctuation. `src/claim-text.ts` renders them as their source
  key instead.
- **Target registration.** Any node with an `identifier` outside a six-type exclusion list
  becomes an xref target.
- **`myst.xref.json`.** Written by the `--site` build, before any HTML rendering, so it does
  not require a theme.
- **Themes.** Resolving a named theme (`book-theme`) downloads it from `api.mystmd.org`. The
  integration test points a copy of the example at a minimal local template
  (`tests/fixtures/site-template/`) so the suite exercises the real site build without a
  network dependency. The example itself uses `book-theme`, as a real publication would, and CI
  builds it that way.
